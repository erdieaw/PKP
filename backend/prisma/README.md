# Database Contract

Prisma 6.19.3, PostgreSQL. All 14 tables use the required snake_case names;
columns retain camelCase. UUID resource IDs are generated by Prisma, not database defaults;
indicator IDs and section codes are natural string keys, not UUIDs.
Use migrations rather than `db push`: CHECK constraints and triggers are SQL-only.
Application locking order starts with singleton `period_settings`, then
`year_periods`, then `period_locks`. Only the selected year permits period writes.
The active-period migration deliberately leaves selection null; Dinkes must
select an existing year through the API. Seed never activates or resets it.
See [active period contract](../ACTIVE_PERIOD.md).

## Catalogue And Seed

Run `node backend/scripts/import-catalogue.mjs` from the repository root to
regenerate `seed-data/catalogue.json`. This checked-in importer is the only step
that reads frontend source. It excludes all 10 Excel header artifacts, preserves
272 operational indicator IDs, and produces 68 sections: 29 top-level plus 39
nested sections. Intermediate ancestors absent from source labels use
`Subbagian <code>` names. Top-level sections have null `parentCode`; they are not
cluster-root nodes. Sections aggregate indicators; no persistent head indicators.
The importer deliberately discards source achievement/history values.

Run the existing backend `db:seed` script after migration. The seed upserts
sections, indicators and year 2026, with `ILP_2026_V1` scoring. Default counts on
an empty database: 68 sections, 272 indicators, one year, zero health centers,
zero users, zero annual targets/assignments/records/locks/uploads/recommendations,
zero audit entries and zero export jobs. Existing operational rows are untouched.
Repeated seeds preserve existing year locks and account passwords/statuses.
Existing section/indicator upserts use `update: {}`: manual edits, labels and
archive states are preserved, not refreshed or reset from the checked-in catalogue.
272 indicators and 68 sections are the initial baseline only. Runtime counts,
submission completeness and reports use the dynamic active catalogue.

## Shared Master Lifecycle

Both `ADMIN_PUSKESMAS` and `DINKES_ADMIN` intentionally manage one global
indicator/section catalogue shared by all tenants. Mutations are audited; DELETE
sets `isActive=false`, and PATCH `isActive:true` restores the same identity.
Historical references remain. A section cannot be archived while active descendant
sections or indicators remain; restoration requires an active parent. Default reads
exclude archived indicators/sections; optional GET `includeArchived=true` is
manager-only. Bulk writes allow at most2000 items; paginated reads at most500.

The additive migration
[`20261019000000_section_is_active`](migrations/20261019000000_section_is_active/migration.sql)
adds `sections.isActive` and has been deployed in the reported environment. Run
`db:deploy` in each environment; do not substitute `db push`.

Once an indicator has monthly records anywhere, changing cluster/section,
targetNumeric, default denominators/targets or polarity returns409. Create a new
indicator ID/version instead. Metadata/archive changes may affect draft/live
reports, but protected snapshots and append-only audits remain unchanged through
the API. This is application immutability, not protection from a database owner.

Center DELETE is soft deactivation by Dinkes and revokes tenant sessions; tenant
admins may edit only their own center profile. Only Dinkes may create years,
edit cutoff, select the active year, change its province switch, lock/unlock or
delete a year. The active year cannot be deleted. Other year deletion is
allowed only without target, assignment, record, period, recommendation, upload or
export-job references. Account DELETE sets `INACTIVE`, preserving historical rows.

## Credentials

- Production-compatible bootstrap: set both `BOOTSTRAP_ADMIN_USERNAME` and
  `BOOTSTRAP_ADMIN_PASSWORD` (at least 12 characters). Creates one tenantless
  `DINKES_ADMIN`; never resets an existing account. Incompatible username
  collisions fail instead of elevating privileges.
- Demo: only when `NODE_ENV != production` and `SEED_DEMO=true`. Requires
  `SEED_DEMO_PASSWORD` of at least 12 characters; there is no default password.
  Creates center `DEMO-001` and usernames `demo.dinkes`, `demo.admin`, `demo.pic`
  with roles `DINKES_ADMIN`, `ADMIN_PUSKESMAS`, `PIC` respectively. Only the latter
  two have a health center. No monthly history or synthetic scores are created.
- Passwords use Argon2id. Seed output never prints credentials or database errors
  that could include query arguments. Services must redact secrets before writing
  arbitrary AuditLog details; JSON contents cannot provide reliable redaction.
- Managed reset (`POST /users/:id/reset-password`) permits an admin to reset only
  their own tenant's PICs, and Dinkes to reset tenant admin/PIC accounts. No peer
  admin or self reset; self changes use `/auth/change-password`. A new password
  of12..256 characters and a nonblank reason are required. The transaction changes
  the hash, increments tokenVersion, revokes all target sessions and audits only
  target/role/reason, never passwords, hashes or tokens. Self-service recovery is
  unavailable and not planned, per the explicit user requirement.

## SQL Protections

The migration enforces tenant presence by role, nonnegative inputs, month and
quarter bounds (export quarter zero means annual), year range 2000..9999,
cutoff day 1..28, and performance score bounds 0..100. Nullable achievement
percentages can exceed 100. Foreign keys restrict deletion except sessions,
which cascade with their user. Submission/verification actor IDs are nullable
User foreign keys. `updatedBy` and `reviewedBy` remain plain strings as specified.

Identity triggers prevent retargeting existing monthly records, targets,
assignments, period locks, recommendations and uploads. Upload filename, MIME
type and size are immutable too. Object keys and etags may change only during
`PENDING -> READY` finalization; only `READY -> ATTACHED` may follow, with no
status regression or later object/etag changes. PIC reassignment itself
remains allowed, but assignment INSERT/UPDATE requires an ACTIVE PIC in the same
health center (the user row is locked FOR SHARE during validation).

Monthly INSERT/UPDATE/DELETE locks `year_periods` FOR UPDATE before checking
locks and rejects locked years or SUBMITTED/VERIFIED periods. A quarterly lock
is YTD: quarter N covers months 1 through N * 3. UPDATE checks both OLD and NEW.
Annual target INSERT/UPDATE/DELETE uses the same ordering and rejects any
submitted/verified period for the tenant/year. Already-locked targets reject
UPDATE/DELETE. A lock-only `isLocked=false -> true` update (plus updatedAt) is
allowed even in a protected year/period; it cannot alter target values.

Audit logs reject UPDATE, DELETE and TRUNCATE. Run the app as a
non-owner database role without trigger-disabling or schema-modification rights.
Application services must still authorize cross-tenant relationships and use the
same year-first lock ordering when submitting/verifying periods; these triggers
do not replace service authorization. User status changes do not retroactively
delete or invalidate historical PIC assignments.

and does not require a shadow database to deploy.
